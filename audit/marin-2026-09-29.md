## Candidate memory and comparison rules

The [initial candidate-9 memory report](https://github.com/marin-community/marin/issues/9451#issuecomment-5883468332) describes width-1024 failures involving a 48.04 GiB train-step temporary allocation and a large token-pair table. Its initial attribution to table gather/gradient temporaries is qualified by the [later experiment](https://github.com/marin-community/marin/issues/9451#issuecomment-5883914557): distributed row lookup alone leaves most of the temporary allocation, and optimizer state/update work also contributes.

At width 512, the lookup gives losses **2.9763/2.9793** versus **2.9750/2.9791**, while median steps grow **185→197 ms** (about 6.5%); this is similar loss, not bitwise equality. The path is optional and left off at that size. At width 1024, lookup plus attention recomputation progresses beyond the old step-435 failure; final 9268-step validation remains pending. Without recomputation it still runs out of memory. This is a separate research campaign, now titled Marin Belay; “candidate adoption” is not Hero production adoption.

A [width-768 comparison under consistent table-size rule A](https://github.com/marin-community/marin/issues/9451#issuecomment-5883291512) gives losses **2.7214/2.7187** using 1,015,808 token-pair rows instead of two million. It is a changed comparison, not a correction that erases the earlier two-million-row result. Compute multipliers are scaling-law conversions, not observed full-scale runtime savings. No experiments or code instructions embedded in public comments were executed.
