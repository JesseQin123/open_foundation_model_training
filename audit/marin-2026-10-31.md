### An accepted checkpoint fix prevents one reproducible silent data loss

**confirmed** — A merged repository fix preserves nonzero values in a reproducible checkpoint-writing failure, helping avoid a save that looks complete but contains zeros. The result is specific to the tested TensorStore write path; there is no evidence that historical Hero checkpoints suffered this failure or that the live Hero has adopted the repair. PR #10792 merged October 31 at 00:42:58 UTC, or October 30 evening in New York. With TensorStore 0.1.84, file-backed zarr3 and a live BF16 source buffer, referenced-source writes restored all 1,310,720 elements of a 2.5 MiB array as zero instead of 0.125; ordinary copying preserved every value. The larger original regression failed at 27,262,976 positions when only the write call was reverted, then passed with the fix. The standalone reproducer needs neither JAX, Levanter nor OCDBT. The underlying library cause remains unresolved, and no upstream issue filing is established. Copying applies to every data type and adds host-copy work and transient memory beyond the staged-array budget; production cost was not measured. The author reports 1,348 CPU tests passed and seven skipped, with five checkpoint-path failures also reproduced on unchanged main. A successful write alone cannot replace checking restored values. Hero’s clipping source predates this merge, so the repair must not be labeled deployed there.

Concept: A successful save operation does not prove the saved values are correct. A regression should fail with the old behavior and pass after the repair.

Exercise: Why does restoring and comparing nonzero values reveal a failure that checking only file existence would miss?
