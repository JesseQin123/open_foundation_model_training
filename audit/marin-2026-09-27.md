## The new communication test

[Open PR #9481](https://github.com/marin-community/marin/pull/9481) follows the [September 24 one-rack profile](https://github.com/marin-community/marin/issues/8317#issuecomment-5821773936). It pipelines two expert chunks, moves smaller collectives outside the transports' windows, and supplies an XProf-derived latency profile to XLA. Reported results on one GB200 rack, checkpoint 144000, batch 1024, production XLA flags:

| Configuration | Communication overlap | Exposed collective time | Step time |
| --- | ---: | ---: | ---: |
| September 24 baseline | 60.5% | 1.51 s | 13.94 s |
| Proposed code | 60.2% | 1.55 s | 14.13 s |
| Code plus program-specific latency profile | 81.0% | 0.88 s | 13.72 s |

The reported loss difference is within 3e-4 at every compared step. Collective busy time increases 3.8→4.6 seconds because overlapping transfers and computation compete. The profile only sees rack-local collectives. The eleven-rack program needs its own profile and validation; the profile is not committed. Production still runs without this profile-guided estimator, so the author explicitly cautions that code alone would slow Hero. This is an experimental result from an open PR, not adopted production performance or an 81% speedup.

## Small-model timing and quality tradeoffs

The [garbage-collection report](https://github.com/marin-community/marin/issues/9451#issuecomment-5851948948) describes a 400-step d512 diagnosis: individual ranks pause 0.40–0.57 seconds at different steps, delaying peers at collectives. Disabling automatic collection during the loop and coordinating explicit collections every 50 steps reduces mean measured duration 213.8→161.7 ms, while medians remain about 160 ms. This is reported small-model evidence, not a reproduced experiment or a new change to Hero's existing coordinated-GC configuration. The post was published September 27 at 02:25 UTC (September 26 evening in New York), after the missing day's saved morning review; it is reported as newly checked today, not backdated. Its nominal budget used median throughput and omitted tail latency; it also excludes startup, evaluation and some metrics work. The reported d768 benefit is a projection, not the same measured d512 outcome. Sustained memory behavior needs separate evidence.

The [fixed-time comparison](https://github.com/marin-community/marin/issues/9451#issuecomment-5854280637) reports that a slower full candidate scores 3.0643 versus baseline 3.0591 when its step budget is reduced, while the candidate without the more expensive ReLU-squared change scores 3.0414. At equal steps that latter candidate scores 3.0325. The distinction supports evaluating both speed and quality under a clearly defined budget, with the timing limitations above; it does not establish a full wall-clock Hero gain.

The [four-size recipe report](https://github.com/marin-community/marin/issues/9451#issuecomment-5854642421) gives matched-step losses 3.1099/2.8114/2.5818/2.4637 versus clean-KMA 3.1215/2.8234/2.5934/2.4710. Its approximately 1.09× compute-equivalent benefit at 10^24 FLOPs is extrapolated using a fitted power law with loss floor 1.2; it is not a measured Hero score or runtime saving. Its newer fixed-time candidate is a separate recipe. Small-model author/agent reports were not independently reproduced; selected public comment bodies are retained for audit.
